## 1. โจทย์และเป้าหมาย

**โจทย์:** สร้างแอปบน iOS และ Android (เขียนด้วย Dart/Flutter) ที่เก็บข้อมูลจากผู้ใช้ขณะเดินทาง แล้ววิเคราะห์การเปลี่ยนแปลงของ **RSSI** (ความแรงสัญญาณ) ของ Wi-Fi AP เพื่อ **จำแนกรูปแบบการเดินทาง** ได้แก่

| โหมด | ความเร็วโดยทั่วไป (ประมาณ) |
|---|---|
| เดิน | ~3–6 km/h |
| ปั่นจักรยาน | ~10–20 km/h |
| ขี่มอเตอร์ไซค์ | ~20–40 km/h (ในมหาวิทยาลัย) |
| ขับรถยนต์ | ~20–40 km/h (ในมหาวิทยาลัย), สูงกว่านอกพื้นที่ |

**บทบาทของ GPS:** ใช้เป็น **ground truth** (ความเร็ว/ตำแหน่งจริง) เพื่อสร้างป้ายกำกับและตรวจสอบความถูกต้องของผลจาก Wi-Fi
**บทบาทของ RSSI:** เป็นฟีเจอร์หลักของโมเดล

### 1.1 คำถามวิจัยที่แนะนำให้ตั้งให้ชัด

เนื่องจากความเร็วจาก GPS แยกเดิน/จักรยาน/ยานยนต์ได้ดีอยู่แล้ว โครงการควรตอบว่า:

> **"RSSI ของ Wi-Fi ช่วยจำแนกโหมดการเดินทางได้เท่าไร ทั้งแบบใช้เดี่ยวและเสริม IMU/GPS และใช้แทน GPS ได้ในสถานการณ์ใด (ในอาคาร, GPS แย่, ประหยัดแบตเตอรี่)"**

ไม่ควรตั้งเป้าว่า RSSI ต้องแยกได้ทุกโหมด โดยเฉพาะมอเตอร์ไซค์กับรถยนต์ที่ความเร็วทับซ้อนกัน

### 1.2 หมายเหตุเรื่องคำศัพท์

"isi" ที่ใช้ในบทสนทนาก่อนหน้า ได้รับการยืนยันแล้วว่าหมายถึง **RSSI** ไม่ใช่ IMSI ดังนั้นประเด็นเรื่อง IMSI ไม่เกี่ยวกับโปรเจกต์นี้

## 2. งานวิจัยฐาน และช่องว่างที่โปรเจกต์นี้เติม

### 2.1 งานของ Jundee et al. (2023) ทำอะไร

- ใช้ log การเชื่อมต่อ Wi-Fi ของ ม.เชียงใหม่ (CMU): 3,116 AP, 26 วัน (9 ม.ค. – 3 ก.พ. 2020), 133,754,260 records, เก็บทุก 5 นาที/AP
- แต่ละ record มี: MAC ของ AP, พิกัด AP, place ID, device ID (hash), **RSSI**, timestamp
- เลือก 4,803 อุปกรณ์ของนักศึกษาหอพัก แล้วพัฒนาอัลกอริทึม 5 ขั้น: Presence → Residence → Stay → Trip → Inflow/Outflow
- ได้ 440,997 trips (สมบูรณ์ 357,287, ไม่สมบูรณ์ 83,710)
- ตรวจสอบกับ ground truth 54 trips จากแอป GPS (1 วินาที/ครั้ง): ค่า threshold ε ที่ดีที่สุดคือ **7 นาที** (accuracy 0.855, recall 0.870, precision 0.979, F1 0.922)
- สร้างเครื่องมือเว็บ **Wi-Flow** (React.js + Deck.gl)

### 2.2 หลักฐานในงานเดิมที่สนับสนุนโปรเจกต์นี้

ผลของเขาแสดงว่า **ความเร็ว/โหมดการเดินทางมีผลต่อข้อมูล Wi-Fi จริง**:

| โหมด | Accuracy ของการตรวจ trip (Table 3) |
|---|---|
| Walking | 0.611 |
| Cycling | 0.833 |
| Motorcycling | 0.923 |
| Driving | 1.000 |

และ Table 1 แสดงว่าประสิทธิภาพเพิ่มขึ้นตามความเร็วเฉลี่ยของ trip (0.680 ที่ 0–8 km/h จนถึง 1.000 ที่ ≥24 km/h)

### 2.3 ช่องว่างงานวิจัย (Research Gap)

| ประเด็น | งานเดิม | โปรเจกต์นี้ |
|---|---|---|
| แหล่งข้อมูล | Log ฝั่งเครือข่าย | **แอปมือถือฝั่งผู้ใช้** (ความถี่สูงกว่า) |
| การใช้ RSSI | เก็บไว้แต่ **ไม่ได้ใช้วิเคราะห์** | **ใช้เป็นฟีเจอร์หลัก** |
| ผลลัพธ์ | Trip และ O-D flow | **Transport mode classification** |
| ความละเอียดเวลา | 5 นาที | ~1 วินาที (ขึ้นกับแพลตฟอร์ม) |
| การจำแนกโหมด | ไม่ได้ทำ (รายงานแค่ผลต่อความแม่นยำ) | **เป็นเป้าหมายหลัก** |

### 2.4 ข้อควรระวังในการอ้างอิงงานเดิม

- ข้อมูลของงานเดิมเก็บทุก 5 นาที/AP และ **ไม่มีป้ายกำกับโหมดการเดินทางโดยตรง** การต่อยอดครั้งนี้จึงเป็นการเปลี่ยนโจทย์ ไม่ใช่การขยายผลโดยตรง
- ผลต่อ trip detection (accuracy ตามโหมด) ไม่ใช่ผลของการจำแนกโหมด ใช้เป็นหลักฐานเชิงแนวโน้มเท่านั้น

## 3. แนวคิดหลัก

### 3.1 ทำไม RSSI จึงบอกโหมดการเดินทางได้

ความเร็วที่ต่างกันทิ้งร่องรอยในสัญญาณ Wi-Fi 4 แบบ:

1. **อัตราการเปลี่ยนของ RSSI** (dB/วินาที): ยิ่งเร็วยิ่งเปลี่ยนเร็ว
2. **Dwell time**: เวลาที่เกาะ AP หนึ่งตัวก่อนย้าย ยิ่งเร็วยิ่งสั้น
3. **อัตรา roaming** (จำนวนครั้งเปลี่ยน AP ต่อนาที)
4. **ความต่อเนื่องของการเชื่อมต่อ**: ยิ่งเร็ว ยิ่งหลุด/เชื่อมไม่ทันบ่อยขึ้น (งานเดิมก็ระบุว่าความเร็วรถกระทบการตรวจจับที่ประตู)

นอกจากนี้ **ตัวถังรถยนต์** (โลหะ) อาจลด RSSI ลง ซึ่งช่วยแยกรถยนต์ออกจากมอเตอร์ไซค์ (ขนาดของผลนี้ต้องวัดเองจากการทดลอง ไม่ควรสมมติค่า)

### 3.2 ตารางสมมติฐาน (ต้องพิสูจน์ด้วยข้อมูลจริง)

| ลักษณะ | เดิน | จักรยาน | มอเตอร์ไซค์ | รถยนต์ |
|---|---|---|---|---|
| อัตราเปลี่ยน RSSI | ช้า | ปานกลาง | เร็ว | เร็วมาก |
| Dwell time ต่อ AP | นาน | ปานกลาง | สั้น | สั้นมาก |
| Roaming rate | ต่ำ | ปานกลาง | สูง | สูงมาก |
| จังหวะจาก accelerometer | จังหวะก้าว (~2 Hz) | จังหวะปั่น | สั่นจากเครื่องยนต์ | สั่นต่ำ ราบเรียบ |
| ผลของตัวถัง | ไม่มี | ไม่มี | น้อย | RSSI ลดลง (ต้องวัด) |

### 3.3 ความสัมพันธ์ RSSI กับระยะ (ใช้เป็นพื้นฐานเท่านั้น)

```
RSSI(d) = A − 10·n·log10(d)        →   d = 10 ^ ((A − RSSI) / (10·n))
```

- A = RSSI ที่ 1 เมตร (ประมาณ −40 ถึง −50 dBm), n = path loss exponent (ในอาคารประมาณ 2.5–4)
- RSSI แกว่ง ±5–10 dB จากการสะท้อนและสิ่งกีดขวาง จึง **เชื่อถือ "แนวโน้ม" ได้มากกว่าค่าเดี่ยว**
- ค่า A และ n ต้อง calibrate เองในพื้นที่จริง

### 3.4 ข้อจำกัดทางกายภาพที่ต้องยอมรับตั้งแต่ต้น

- **ความผันผวนสูงโดยธรรมชาติ:** multipath, fading, ร่างกายผู้ใช้บัง, ตำแหน่งเครื่อง (กระเป๋า/มือ/ที่ยึด) อาจทำให้ความแปรปรวนที่ความเร็วเดียวกันมากกว่าความต่างระหว่างโหมด
- **ตัวถังรถและโลหะ** ลดทอนสัญญาณ เป็นได้ทั้งตัวช่วยแยกและตัวแปรกวน (ขึ้นกับรถแต่ละคัน)
- **AP นอกอาคารมีน้อย:** การเดินทางด้วยยานยนต์ส่วนใหญ่อยู่บนถนน AP มักอยู่ในอาคาร ทำให้ข้อมูลขาดหายมาก
- **พฤติกรรม roaming ขึ้นกับอุปกรณ์:** แต่ละรุ่นมี roaming threshold ต่างกัน (sticky client) จึงไม่ได้สะท้อนความเร็วอย่างเดียว
- **AP ต่างกันที่กำลังส่ง/ช่องสัญญาณ/คลื่น (2.4 vs 5 GHz)** ต้อง normalize
- **ต้องเชื่อมต่อ Wi-Fi อยู่ก่อน:** ถ้าปิด Wi-Fi หรือไม่ auto-join (เช่น เครือข่ายที่ต้อง login) จะไม่มีข้อมูล RSSI ของ AP ที่เชื่อมอยู่เลย

## 4. ข้อเท็จจริงเรื่องข้อจำกัดของ iOS และ Android

ข้อจำกัดนี้มาจากระบบปฏิบัติการ ไม่ใช่ภาษาโปรแกรม

### 4.1 ตารางเปรียบเทียบความสามารถ

| ความสามารถ | Android | iOS |
|---|---|---|
| GPS (พิกัด ความเร็ว ทิศ) | ได้ | ได้ |
| **BSSID ของ AP ที่เชื่อมอยู่** | ได้ | ได้ ผ่านคำสั่ง **Get Network Details ใน Shortcuts** (หรือผ่าน `NEHotspotNetwork` ต้อง entitlement "Access WiFi Information" + สิทธิ์ Location) |
| **RSSI ของ AP ที่เชื่อมอยู่** | ได้ เป็น **dBm** | ได้ เป็น **dBm ผ่าน Shortcuts** (ผู้วิจัยยืนยันว่าเก็บได้จริง) ส่วนผ่าน `NEHotspotNetwork.signalStrength` เอกสาร Apple ระบุเป็น 0.0–1.0 และมีรายงานว่าอาจคืน 0.0 (**ยังไม่ยืนยัน**) |
| สแกน AP รอบข้างหลายตัว + RSSI | ได้ (throttle ราว 4 ครั้ง/2 นาที; ปิดได้บนเครื่องทดสอบผ่าน Developer Options) | **ไม่ได้** สำหรับแอปทั่วไป (ต้อง entitlement `NEHotspotHelper` ซึ่ง Apple อนุมัติยาก) |
| Cell tower | ได้ | ไม่ได้ |
| Accelerometer / Gyro / Pedometer / Compass | ได้ | ได้ |
| ทำงานตอนปิดจอ | Foreground Service + notification | Background mode `location` (+ ต้องทดสอบว่า Shortcut/Automation รันต่อเนื่องได้เมื่อล็อกจอ) |

**ความต่างหลักมี 3 เรื่อง:**
1. Android เห็นหลาย AP แต่ iOS เห็นเฉพาะ AP ที่เชื่อมอยู่
2. วิธีเก็บ RSSI บน iOS (Shortcuts) **ความถี่และความเสถียรยังเป็นข้อสงสัยหลัก** แม้อ่านค่าได้
3. หน่วยและความละเอียดของ RSSI อาจต่างกันตามแหล่ง (dBm จาก Shortcuts, 0–1 จาก `NEHotspotNetwork`) เทียบตรงๆ ไม่ได้

**ผลต่อการออกแบบ:** ฟีเจอร์ที่ใช้ร่วมกันได้ทั้งสองระบบต้องคำนวณจาก **AP ที่เชื่อมอยู่** เท่านั้น ส่วนฟีเจอร์จากการสแกนหลาย AP เป็นส่วนเสริมของ Android

### 4.2 iOS: วิธีเก็บ RSSI ที่ต้องเปรียบเทียบ

| วิธี | หน่วย | ข้อดี | ข้อเสีย/ความเสี่ยง |
|---|---|---|---|
| **Shortcuts: Get Network Details** | dBm | ยืนยันแล้วว่าอ่านค่าได้ | ไม่มี trigger ระดับวินาที ต้องพึ่ง loop ภายใน Shortcut หรือ automation; รันเบื้องหลังตอนปิดจอไม่แน่นอน; ต้องตั้งค่าเริ่มต้น (แก้ไขโดยแจกลิงก์ iCloud Shortcut สำเร็จรูปให้ผู้เข้าร่วมที่เป็นนักศึกษาวิศวกรรมคอมพิวเตอร์ และติดตั้งแอปผ่าน GitHub Releases + Sideloadly สำหรับใช้ในงานวิจัยเท่านั้น) |
| **`NEHotspotNetwork.fetchCurrent()`** | 0.0–1.0 (ถ้าคืนค่าจริง) | เรียกจากโค้ดแอปโดยตรง ทำงานคู่กับ location background ได้ | ความละเอียดต่ำ และมีรายงานว่าคืน 0.0 (ต้องทดสอบเอง) ต้อง entitlement + สิทธิ์ Location |
| **`NEHotspotHelper`** | dBm (สแกนหลาย AP) | ได้ AP รอบข้าง | Apple อนุมัติเฉพาะแอปเครือข่าย/องค์กรเป็นหลัก ไม่ควรวางแผนพึ่งพา อาจลองยื่นผ่านมหาวิทยาลัยเป็นทางเสริม |

### 4.3 Android: ข้อจำกัดที่ต้องรู้

- **Scan throttling:** Android 9+ จำกัดราว 4 ครั้ง/2 นาที (foreground) และน้อยกว่านั้นใน background จึงสแกนหลาย AP ที่ความถี่สูงไม่ได้ (ปิดได้บนเครื่องทีมวิจัยผ่าน Developer Options เท่านั้น)
- **API เปลี่ยนบ่อย:** `WifiManager.getConnectionInfo()` ถูก deprecate ควรใช้ `ConnectivityManager.NetworkCallback` ร่วมกับ `FLAG_INCLUDE_LOCATION_INFO` และต้องขอสิทธิ์ตำแหน่ง (กับ `NEARBY_WIFI_DEVICES` ใน Android 13+)
- **อัตราอัปเดต RSSI ของ AP ที่เชื่อมอยู่** ไม่รับประกัน 1 Hz และต่างกันตามผู้ผลิต
- **Battery optimization ของผู้ผลิต** (Xiaomi, OPPO, Vivo, Huawei) อาจฆ่า Foreground Service ต้องมีคู่มือให้ผู้ใช้ปิดการประหยัดแบต
- **Flutter:** ต้องเขียน native channel เองหลายจุด ปลั๊กอินสำเร็จรูปมักให้แค่ BSSID/SSID ไม่ครอบคลุม RSSI แบบต่อเนื่อง

### 4.4 สิ่งที่ยังไม่ยืนยัน (ต้องทดสอบในเฟส 1)

- [ ] Shortcut รัน Get Network Details ได้ถี่แค่ไหนจริง ทั้งจอเปิดและจอปิด
- [ ] Loop (Repeat + Wait) ในรันเดียวทำงานได้นานเท่าไรก่อนระบบหยุด
- [ ] Shortcut ส่งค่าเข้าแอปผ่าน App Intent ได้เสถียรเมื่อแอปอยู่เบื้องหลังหรือไม่
- [ ] `NEHotspotNetwork.signalStrength` คืนค่าจริงหรือ 0.0 บน iOS เวอร์ชันที่ใช้
- [ ] Android รุ่นต่างๆ อัปเดต RSSI ที่เชื่อมอยู่ทุกกี่วินาที

## 5. แหล่งข้อมูลตำแหน่ง AP (JumboMap)

> **ส่วนนี้คือจุดที่แทรกลิงก์ JumboMap: <https://jumbomap.cmu.ac.th/>**

### 5.1 บทบาทของ JumboMap ในโปรเจกต์

เว็บ **JumboMap ของ ม.เชียงใหม่** (<https://jumbomap.cmu.ac.th/>) ถูกเสนอให้ใช้เป็น **แหล่งอ้างอิงในการระบุ/ตรวจสอบตำแหน่ง AP** เพื่อสร้าง **ตารางตำแหน่ง AP** (BSSID → พิกัด → ชื่อสถานที่) ซึ่งเป็นข้อมูลตั้งต้นที่ทุกขั้นตอนต่อไปต้องใช้:

| ขั้นตอนที่ต้องใช้ตารางตำแหน่ง AP | ใช้ทำอะไร |
|---|---|
| แปลง roaming sequence เป็นเส้นทาง | รู้ว่าย้ายจาก AP ไหนไปไหน |
| คำนวณระยะ AP-to-AP ÷ เวลา | ประมาณ **ความเร็ว** (ฟีเจอร์ที่ใช้ได้ทั้ง iOS/Android) |
| เทียบกับ GPS | ตรวจความถูกต้อง |
| จัดกลุ่ม AP เป็น place | ทำ stay detection แบบงานเดิม |

### 5.2 ข้อมูลที่ต้องได้จากตารางตำแหน่ง AP

| ฟิลด์ | ความจำเป็น |
|---|---|
| BSSID (ครบทุกตัว: 2.4 GHz, 5 GHz, หลาย SSID) | จำเป็นมาก |
| ละติจูด/ลองจิจูด | จำเป็นมาก |
| ชื่ออาคาร/สถานที่ (place ID) | จำเป็น |
| ชั้น/ตำแหน่งภายในอาคาร | แนะนำ |
| วันที่ตรวจสอบล่าสุด | แนะนำ (AP อาจถูกย้าย) |

### 5.3 สิ่งที่ยังต้องตรวจสอบเกี่ยวกับ JumboMap (ยังไม่ได้ยืนยัน)

เคยพยายามเปิดเว็บนี้แล้ว แต่ **ระบบของเว็บไม่อนุญาตให้เครื่องมืออัตโนมัติเข้าถึง** จึง **ไม่ทราบว่า JumboMap มีฟีเจอร์อะไรบ้างจริงๆ** กรุณาตรวจสอบเองก่อนวางแผนต่อ:

- [ ] JumboMap แสดงตำแหน่ง **AP / BSSID** หรือแสดงแค่แผนที่อาคารและสถานที่? (โดยทั่วไปแผนที่เว็บมักไม่เปิดเผย BSSID ทุกคลื่น/ทุก SSID และหนึ่ง AP มีหลาย BSSID)
- [ ] ถ้าแสดงเฉพาะอาคาร ต้องหาข้อมูล BSSID จากแหล่งอื่น (ดูข้อ 5.4)
- [ ] มี API หรือ export ข้อมูลไหม หรือดูได้ผ่านหน้าเว็บเท่านั้น
- [ ] เงื่อนไขการใช้งาน (ToS) อนุญาตให้นำข้อมูลไปใช้วิจัยหรือไม่

> **ข้อควรระวัง:** เนื่องจากเว็บจำกัดการเข้าถึงอัตโนมัติ **ไม่ควรเขียนสคริปต์ scrape ข้อมูล** (อาจขัดเงื่อนไขการใช้งาน และเป็นข้อมูลโครงสร้างพื้นฐานของมหาวิทยาลัย) ควรติดต่อเจ้าของข้อมูลโดยตรง

### 5.4 ทางเลือกในการได้ข้อมูลตำแหน่ง AP

| วิธี | ข้อดี | ข้อเสีย |
|---|---|---|
| ขอจาก **ITSC ม.เชียงใหม่** โดยตรง (งานเดิมก็ขอบคุณ ITSC ที่ให้ข้อมูล Wi-Fi) — **ควรเป็นแผนหลัก ไม่ใช่แผนสำรอง** | ครบถ้วน ถูกต้อง ถูกต้องตามกฎ | ต้องขอและรออนุมัติ |
| ดูจาก JumboMap แล้วบันทึกด้วยมือ | เริ่มได้เร็ว | อาจไม่มี BSSID ใช้เวลามาก |
| ตัวอย่าง AP ของ Wi-Flow (<https://wiflow.citycontext.info/sample>) | เป็นไฟล์ตัวอย่างตำแหน่ง AP ของ CMU | เป็นตัวอย่าง อาจไม่ครบและไม่ทันสมัย |
| ผู้ใช้เก็บข้อมูลสร้างแผนที่ AP เอง (crowdsourcing / war-walking บน Android) | ได้ BSSID จริง | ใช้เวลาและต้องประมาณตำแหน่ง |

> **หมายเหตุ:** ฟีเจอร์หลัก (RSSI, roaming, dwell time, IMU) **ไม่ต้องรู้ตำแหน่ง AP** ตารางตำแหน่ง AP จำเป็นเฉพาะฟีเจอร์ความเร็วโดยประมาณจาก roaming และการเทียบกับ GPS ดังนั้นการไม่ได้ตารางนี้ไม่ทำให้โครงการล้ม

### 5.5 วิธีใช้ JumboMap ในกระบวนการทำงาน (ถ้ามีข้อมูล AP)

1. เปิด JumboMap เพื่อ **ระบุสถานที่/อาคารและตำแหน่งจริง** ของ AP หรือพื้นที่ทดลอง
2. จับคู่กับ BSSID ที่แอปอ่านได้จริงในพื้นที่นั้น
3. บันทึกลงตารางตำแหน่ง AP (CSV) พร้อมวันที่ตรวจสอบ
4. ใช้เป็นพื้นฐานของ stay/trip detection และการคำนวณความเร็วโดยประมาณ

## 6. สถาปัตยกรรมระบบ

```
[GPS 1 Hz]  [Wi-Fi ที่เชื่อมอยู่: BSSID + RSSI]  [Accelerometer/Gyro/Pedometer]
   Android: WifiManager / NetworkCallback
   iOS: Shortcut (Get Network Details) → App Intent → แอป
                (+ Android: สแกนหลาย AP)
                          ↓
      [Background: Foreground Service (Android) / Background mode `location` (iOS)]
                          ↓
   [ฐานข้อมูลในเครื่อง drift (SQLite): แถวละ 1 observation]
        (iOS: ถ้า App Intent ทำงานนอกโพรเซสหลัก ใช้ App Group container ร่วมกัน)
                          ↓
                 [Auto-Export CSV → บีบอัด In-Memory ZIP (.csv.zip) → อัปโหลดขึ้น Google Drive ผ่าน Google Apps Script (GAS)]
                          ↓
   [Python: ตารางตำแหน่ง AP → Segment → Feature → Classifier → Evaluate]
```

**หลักออกแบบ:** เก็บ **ข้อมูลดิบ** ในแอป แล้ววิเคราะห์ใน Python ภายหลัง เพื่อปรับสูตรและโมเดลโดยไม่ต้อง build แอปใหม่

### 6.1 ส่วนที่ใช้โค้ดร่วมกัน / แยก

| ส่วน | ร่วมกัน? | เครื่องมือ |
|---|---|---|
| UI, ฐานข้อมูล, export, คำนวณ | ร่วม 100% | Flutter + `drift` |
| GPS | ร่วม | `geolocator` |
| Sensors | ร่วม | `sensors_plus` |
| อ่าน BSSID + RSSI ที่เชื่อมอยู่ | **แยก** | Android: Platform Channel (Kotlin) / iOS: Shortcut + App Intent (Swift) และ/หรือ `NEHotspotNetwork` |
| สแกนหลาย AP | **Android เท่านั้น** | `wifi_scan` |
| Background และสิทธิ์ | **แยกตั้งค่า** | `Info.plist` / `AndroidManifest.xml` |

(ประมาณการว่าโค้ดใช้ร่วมกันได้ราว 70–80% เป็นการประเมินคร่าวๆ ไม่ใช่ตัวเลขตายตัว; ควรตรวจเวอร์ชัน package บน pub.dev ก่อนใช้งาน)

### 6.2 ทิศทางการเรียกระหว่างแอปกับ Shortcuts (iOS)

- **ทิศทางที่ถูกต้อง:** Shortcut เรียก App Intent ของแอปเรา (เช่น `LogWifiSample(rssi, bssid, ssid, timestamp)`)
- **ทิศทางที่ไม่เหมาะ:** แอปสั่งรัน Shortcut ผ่าน URL scheme เพราะจะสลับหน้าจอไปแอป Shortcuts (foreground) ใช้เก็บเบื้องหลังไม่ได้
- ทางสำรอง: ให้ Shortcut ต่อบรรทัดลงไฟล์ CSV แล้วนำเข้าแอปทีหลัง (ช้ากว่าแต่ทดสอบง่าย)

## 7. ข้อมูลที่ต้องเก็บ (Schema)

เก็บเป็น event stream มี metadata บอกที่มา เพราะเก็บไม่ครบแล้วย้อนกลับมาแก้ไม่ได้

| ฟิลด์ | ตัวอย่าง | หมายเหตุ |
|---|---|---|
| `timestamp` / `t_utc_ms` | ms precision | wall-clock UTC |
| `t_mono_ns` | int | เวลา monotonic ของเครื่อง (ใช้ซิงก์ภายในเครื่อง) |
| `session_id` | UUID | หนึ่งการเดินทาง |
| `participant_id` | รหัสนิรนาม | ห้ามใช้ชื่อ/เบอร์ ใช้แบ่งข้อมูลแบบ leave-one-participant-out |
| `type` / `source` | `gps` / `wifi_connected` / `wifi_scan` / `accel` / `gyro` / `label` | |
| `platform` | `ios` / `android` | |
| `device_model`, `os_version` | iPhone 13 / Pixel 7 | RSSI ต่างรุ่นต่างค่า |
| `bssid` (hash เมื่ออัปโหลด) | AA:11:... | hash ด้วย salt |
| `ssid` | | |
| `rssi_raw` | −52 หรือ 0.74 | เก็บค่าดิบ |
| `rssi_unit` | `dbm` / `norm01` | แยกหน่วย |
| `rssi_source` | `wifimanager` / `shortcut` / `nehotspot` | บอกวิธีเก็บ เพื่อวิเคราะห์ความต่างของแหล่ง |
| `lat`, `lon`, `speed`, `accuracy` | | จาก GPS |
| `accel_x/y/z`, `gyro_x/y/z` | | ความถี่ตาม sensor |
| `user_label_mode` | walk / bike / motorcycle / car / bus | **Ground Truth:** ผู้ใช้กดระบุเอง (เลือกได้อิสระก่อนเริ่ม ระหว่างทริป Quick Tag และหลังหยุด) |
| `activity_recognition_mode` | still / walking / on_bicycle / in_vehicle | **Baseline Prediction:** โหมดที่ระบบ OS ตรวจจับได้อัตโนมัติ (Google Activity Recognition API) ใช้เป็น Benchmark เปรียบเทียบ |
| `phone_position` | pocket / hand / bag / mount | ตำแหน่งที่วางมือถือ มีผลต่อสัญญาณและ accelerometer |

**หลักการซิงโครไนซ์ข้อมูล (Synchronized Snapshot Engine):** 
1. บันทึกข้อมูลด้วยรอบความถี่ 1 วินาที โดยจับภาพ State ล่าสุดของเซ็นเซอร์ทุกตัว (GPS, IMU, Wi-Fi RSSI) ลงเป็น 1 แถวสมบูรณ์พร้อมกัน (`type: sync_sample`)
2. ใช้กลไก Forward-Fill เพื่อป้องกันช่องว่าง (Zero Blank Cells) ให้ไฟล์ CSV สมบูรณ์ 100% พร้อมเทรนโมเดล ML ทันที
3. เวลา UTC (`t_utc_ms`) และเวลา Monotonic (`t_mono_ns`) ถูกบันทึกกำกับทุกแถวในระดับนาโนวินาทีเพื่อความแม่นยำสูงสุด

## 8. วิธีวิเคราะห์ (Pipeline และ Feature)

### 8.1 Pipeline

1. **Preprocess:** ซิงก์เวลา, กรองค่าผิดปกติ (RSSI นอกช่วงประมาณ −20 ถึง −100 dBm), กรอง RSSI ด้วย exponential moving average (ขั้นสูงค่อยใช้ Kalman filter)
2. **Resample:** กริด 1 วินาที RSSI ใช้ forward-fill จำกัดจำนวนวินาที ส่วนที่เกินให้ทำเครื่องหมาย "ขาดหาย" ไม่ interpolate ยาว
3. **Segmentation:** ตัดเป็นช่วงการเคลื่อนที่ (ใช้แนวคิด stay detection ของงานเดิม โดย ε = 7 นาทีเป็นจุดเริ่มต้น แล้วปรับตามข้อมูล)
4. **Windowing:** แบ่งเป็นหน้าต่างเวลา (10, 30, 60 วินาที ซ้อนทับ 50%) แล้วคำนวณฟีเจอร์ เลือกขนาดที่ดีที่สุดด้วย validation
5. **Normalization:** แยกตามแพลตฟอร์ม/รุ่นอุปกรณ์/คลื่น 2.4–5 GHz หรือใช้ฟีเจอร์ความต่างที่ไม่ขึ้นกับหน่วย
6. **Labeling:** ใช้ GPS speed + ปุ่มที่ผู้ใช้กดระบุโหมด ติดป้าย window ตามโหมดที่ครอบครองเกิน 80% ไม่เช่นนั้นทิ้ง และแยกคลาส "หยุดนิ่ง/ติดไฟแดง"
7. **Train/Evaluate:** Random Forest / XGBoost เป็น baseline ก่อน แล้วค่อยลอง CNN/LSTM

### 8.2 ฟีเจอร์

| กลุ่ม | ฟีเจอร์ | iOS | Android |
|---|---|---|---|
| อัตราเปลี่ยนสัญญาณ | mean/max/เปอร์เซ็นไทล์ 90 ของ \|ΔRSSI/Δt\| | ✔ (ขึ้นกับความถี่ที่เก็บได้) | ✔ (dBm) |
| สถิติ | mean, variance, std, skewness, IQR ของ RSSI | ✔ | ✔ |
| รูปแบบสัญญาณ | zero-crossing ของอนุพันธ์, พลังงานแถบความถี่ต่ำ/สูง (ถ้าความถี่พอ) | ✔ (ถ้าถี่พอ) | ✔ |
| Roaming | จำนวนครั้งเปลี่ยน AP/นาที, dwell time (mean/median/min), จำนวน AP ไม่ซ้ำ | ✔ | ✔ |
| ความต่อเนื่อง | gap ratio (สัดส่วนช่วงที่ไม่มีการเชื่อมต่อ), จำนวนครั้งที่หลุด | ✔ | ✔ |
| ความเร็วโดยประมาณ | ระยะ AP-to-AP ÷ เวลาย้าย (ต้องใช้ตารางตำแหน่ง AP) | ✔ | ✔ |
| Accelerometer | ความถี่หลัก, พลังงานที่ความถี่ก้าวเดิน (~1.5–2.5 Hz), ความสั่นความถี่สูง | ✔ | ✔ |
| GPS (baseline/ground truth) | ความเร็วเฉลี่ย/สูงสุด/ความแปรปรวน, ความเร่ง, การเปลี่ยนทิศ | ✔ | ✔ |
| หลาย AP พร้อมกัน | จำนวน AP ที่เห็น, ความต่าง RSSI ระหว่าง AP | ✘ | ✔ |

### 8.3 โมเดลเปรียบเทียบ (เป็นผลงานวิจัยในตัว)

- **โมเดล A (ข้ามแพลตฟอร์ม):** ใช้เฉพาะฟีเจอร์ที่ iOS มี
- **โมเดล B (Android เต็ม):** เพิ่มฟีเจอร์สแกนหลาย AP
- ดูว่า B ดีกว่า A เท่าไร = **คุณค่าของข้อมูลที่ iOS ขาด**
- ถ้า RSSI จากสองแพลตฟอร์มหน่วยหรือความละเอียดต่างกัน ควร **normalize แยกตามแพลตฟอร์ม** หรือใช้ฟีเจอร์ที่ไม่ขึ้นกับหน่วย (เช่น อัตราการย้าย AP, dwell time) และตรวจว่าโมเดลที่ฝึกบนแพลตฟอร์มหนึ่งใช้กับอีกแพลตฟอร์มได้แค่ไหน

### 8.4 ชุดฟีเจอร์ที่ต้องเปรียบเทียบ (Ablation)

| ชุด | ฟีเจอร์ | ตอบคำถาม |
|---|---|---|
| G | GPS อย่างเดียว | เพดานของวิธีปกติ |
| I | IMU อย่างเดียว | ทางเลือกประหยัดแบต |
| R | RSSI/Roaming อย่างเดียว | **แกนของโครงการ** |
| R+I | RSSI + IMU | แทน GPS ได้ไหม |
| G+R, G+I, G+R+I | Fusion | RSSI เพิ่มค่าเท่าไร |
| R (Android) vs R (iOS) | แยกแพลตฟอร์ม | ผลกระทบของความถี่/แหล่งข้อมูลที่ต่างกัน |

## 9. การออกแบบการทดลองและการวัดผล

### 9.1 การเก็บข้อมูล

1. **Calibrate (Android):** วัด RSSI ที่ 1, 2, 5, 10 เมตร เพื่อหา A และ n ของพื้นที่จริง
2. เก็บข้อมูลทั้ง 4 โหมด หลายเส้นทาง หลายรอบ หลายช่วงเวลา **หลายคน หลายรุ่นเครื่อง หลายตำแหน่งวางเครื่อง**
3. ใช้ Wi-Fi AP ของพื้นที่ที่มีผังตำแหน่งชัดเจน (ดูหัวข้อ 5)
4. ปิด Wi-Fi scan throttle บนเครื่อง Android ทดสอบ (Developer Options)
5. ต้องเชื่อมต่อ Wi-Fi ตลอดทางเดิน (บน iOS ถ้าไม่ต่อ Wi-Fi จะไม่มีข้อมูล AP)
6. ป้ายกำกับ: ให้ผู้ใช้กด Start/Stop ระบุโหมดจริง (self-report) แล้วใช้ GPS ตรวจสอบ เพราะใช้ความเร็ว GPS อย่างเดียวติดป้ายอาจผิดในจุดหยุดรถ/ไฟแดง

### 9.2 ขนาดตัวอย่าง

งานเดิมใช้ ground truth เพียง 54 trips ซึ่งน้อยมากสำหรับ ML ควรตั้งเป้าอย่างน้อยหลายร้อยช่วงต่อโหมด (ตัวเลขเป้าหมายเป็นข้อเสนอ ต้องปรับตามกำลังการเก็บข้อมูลจริง) และต้องมีหลายอุปกรณ์/หลายคนเพื่อไม่ให้โมเดล overfit กับเครื่องใดเครื่องหนึ่ง

### 9.3 ตัวชี้วัด

| ตัวชี้วัด | ความหมาย |
|---|---|
| Accuracy, Precision, Recall, F1 (ต่อคลาส) | คุณภาพโดยรวมและรายโหมด |
| **Macro-F1, Balanced accuracy** | ใช้แทน accuracy อย่างเดียว เพราะคลาสไม่สมดุล (ทริปเดินมักมากสุด) |
| **Confusion matrix** | ดูว่าสับสนระหว่างโหมดใด (สำคัญที่สุด) |
| เทียบ Model A vs B | คุณค่าของการสแกนหลาย AP |
| เทียบ iOS vs Android | ผลของความต่างแพลตฟอร์ม |
| **Baseline: GPS speed อย่างเดียว** | RSSI ต้องมีข้อได้เปรียบอย่างอื่น เช่น ใช้ในอาคาร/ที่ GPS ไม่ดี หรือประหยัดแบตเตอรี่ |
| Feature importance / SHAP | ฟีเจอร์ RSSI ตัวใดมีผล และสอดคล้องกับสมมติฐานหรือไม่ |

### 9.4 หลักการแบ่งข้อมูล

**แบ่ง train/test ตาม "คน" และ "รุ่นเครื่อง" (Leave-One-Participant-Out หรือ GroupKFold ตามผู้เข้าร่วม/ทริป) ไม่ใช่ตามช่วงเวลา และไม่สุ่มระดับ window** มิฉะนั้นเกิด data leakage และผลดีเกินจริง

### 9.5 คู่ที่คาดว่าจะสับสน

- จักรยาน ↔ มอเตอร์ไซค์ (ความเร็วทับซ้อน)
- **มอเตอร์ไซค์ ↔ รถยนต์ (ความเร็ว 20–40 km/h เหมือนกัน ทับซ้อนทั้งรูปแบบ roaming — คาดว่ายากที่สุด ควรรวมเป็นคลาส "ยานยนต์" ในผลหลัก และใช้ IMU หรือระดับการลดทอนสัญญาณช่วย)**
- เดิน ↔ จักรยาน (ความเร็วต่ำ)

### 9.6 สถานการณ์ที่ต้องรายงานแยก

- ในอาคาร/ใต้หลังคา (GPS แย่) vs กลางแจ้ง
- ความหนาแน่น AP สูง vs ต่ำ
- ตำแหน่งวางเครื่อง: กระเป๋า / มือ / ที่ยึด
- รถยนต์ vs มอเตอร์ไซค์ (ผลของตัวถังต่อสัญญาณ)
- Android vs iOS และฝึกบนแพลตฟอร์มหนึ่ง ทดสอบอีกแพลตฟอร์ม

| ปัญหา | ผลกระทบ | วิธีรับมือ |
|---|---|---|
| RSSI แกว่ง ±5–10 dB | ค่าเดี่ยวไม่น่าเชื่อถือ | กรอง ใช้แนวโน้มและสถิติในหน้าต่าง |
| Sticky client (ยึด AP เดิมนานเกิน) | จุดย้าย AP ≈ กึ่งกลางระหว่างสอง AP | ใช้จุดกึ่งกลางเป็นตำแหน่งประมาณ |
| หนึ่ง AP หลาย BSSID | จับคู่ผังไม่ติด | ตารางต้องครบทุก BSSID |
| ต่างรุ่นต่างค่า RSSI / roaming threshold ต่างกัน | เทียบข้ามเครื่องคลาดเคลื่อน | บันทึกรุ่นเครื่อง, calibrate ต่อรุ่น, ใช้ฟีเจอร์ที่ไม่ขึ้นกับหน่วย |
| **iOS: Shortcuts ความถี่ต่ำ / ถูกระบบหยุดตอนปิดจอ / เปลี่ยนพฤติกรรมตามเวอร์ชัน** | ข้อมูล iOS ห่างหรือขาด คำนวณ dB/s ไม่ได้ | วัดในเฟส 1 ตั้งเกณฑ์ go/no-go; ล็อกเวอร์ชัน iOS ผู้เข้าร่วม; มีทางสำรอง CSV; ถ้าไม่ผ่านให้ iOS เป็นกลุ่มเปรียบเทียบใช้เฉพาะฟีเจอร์หยาบ |
| **iOS: ภาระผู้ใช้ (ต้องตั้ง Automation / Sideload แอป)** | ผู้ใช้ทั่วไปทำเองได้ยากหรือหลุดจากการเก็บข้อมูล | ใช้กลุ่มอาสาสมัครที่เป็นนักศึกษาวิศวกรรมคอมพิวเตอร์ แจกไฟล์ผ่าน GitHub Releases (ติดตั้งด้วย Sideloadly + Free Apple ID ของตนเอง) พร้อมแนบลิงก์ iCloud Shortcut สำเร็จรูปและตรวจข้อมูลรายวัน |
| iOS: `NEHotspotNetwork.signalStrength` อาจเป็น 0.0 หรือหน่วย 0–1 | ใช้เป็นฟีเจอร์ไม่ได้/เทียบ dBm ไม่ได้ | ทดสอบเทียบ แยก normalize หรือแยกโมเดล |
| iOS ไม่ต่อ Wi-Fi = ไม่มีข้อมูล | ข้อมูลขาด | ตรวจและแจ้งผู้ใช้ |
| iOS: แอปที่พึ่ง workaround อาจมีปัญหา App Store review | เผยแพร่สาธารณะบนสโตร์ไม่ได้ | ใช้ภายในงานวิจัยเท่านั้น โดยแจกจ่ายไฟล์ `.ipa` จาก GitHub Actions ให้ผู้เข้าร่วมติดตั้งผ่าน Sideloadly |
| **Android: Foreground Service ถูกฆ่าตามยี่ห้อ** | ข้อมูลหาย | คู่มือตั้งค่ารายยี่ห้อ ตรวจสอบรายวัน ทดสอบหลายยี่ห้อ |
| Android: อัตราอัปเดต RSSI ไม่แน่นอน | ฟีเจอร์ที่ใช้อนุพันธ์ผิดเพี้ยน | วัดจริงในเฟส 1 ใช้ window ยาวขึ้น |
| รถยนต์เร็วเกินไป เชื่อมไม่ทัน | ข้อมูลขาดหาย | ถือ gap ratio เป็นฟีเจอร์ |
| AP ในที่โล่ง/ถนนมีน้อย | ฟีเจอร์ไม่ครบ | ใส่ "ขาดหาย" เป็นฟีเจอร์ รายงานผลแยกพื้นที่ |
| **มอเตอร์ไซค์ vs รถยนต์ แยกไม่ได้** | F1 ของคลาสนี้ต่ำ | รายงานตามจริง รวมเป็นยานยนต์ในผลหลัก |
| ตำแหน่งเครื่อง (มือ/กระเป๋า) | สัญญาณและ accelerometer เปลี่ยน | บันทึกเป็น metadata |
| ผู้โดยสาร vs คนขับ | Wi-Fi แยกไม่ได้ | กำหนดขอบเขตว่าจำแนก "โหมดการเคลื่อนที่" ไม่ใช่บทบาท |
| GPS ในอาคารคลาด 10–50 ม. | ใช้เป็น ground truth ในอาคารไม่ได้ | ทดลองกลางแจ้งหรือใช้จุดอ้างอิงที่วัดจริง |
| Time sync ระหว่าง GPS/Wi-Fi/IMU (โดยเฉพาะ iOS ที่ผ่าน Shortcut) | ฟีเจอร์ผิด | ใช้ clock เดียว วัด offset ในเฟส 1 |
| Class imbalance | accuracy หลอกตา | ใช้ macro-F1, balanced accuracy, class weights |
| Data leakage | ผลดีเกินจริง | แบ่งตามคน/ทริป |
| ผู้เข้าร่วมน้อย/อุปกรณ์ซ้ำกัน | Overfit กับอุปกรณ์ | LOPO-CV และรายงานข้อจำกัดชัดเจน |
| สภาพแวดล้อมเดียว (มหาวิทยาลัย) | สรุปทั่วไปไม่ได้ | ระบุเป็นข้อจำกัดของงาน |
| ผังตำแหน่ง AP ล้าสมัย / ไม่ได้ตารางจาก ITSC | ตำแหน่งผิด/ฟีเจอร์ตำแหน่งหาย | ใส่วันที่ตรวจสอบ; ฟีเจอร์หลักไม่ต้องใช้ตำแหน่ง AP; ประมาณจากข้อมูลเองเป็นสำรอง |

## 11. ความเป็นส่วนตัวและกฎหมาย

BSSID + พิกัด + เวลา ระบุพฤติกรรมของบุคคลได้ (BSSID บ้านเทียบเท่าที่อยู่) แม้ไม่มีชื่อก็ระบุตัวตนได้ทางอ้อม จึงต้อง:

- ขอ **consent ที่ชัดเจน** (PDPA ไทย) บอกว่าเก็บอะไร (ตำแหน่ง, BSSID, เซนเซอร์เคลื่อนไหว) เพื่ออะไร นานเท่าไร
- **hash BSSID** ก่อนอัปโหลด และไม่เก็บ AP ของบ้านผู้ใช้ (ตัดช่วงที่พัก/ต้นปลายทริปด้วย geofence)
- ให้ผู้ใช้ **ลบข้อมูลตัวเอง** ได้ และมีนโยบายลบข้อมูล
- เก็บในเครื่องก่อน อัปโหลดเมื่อผู้ใช้ยินยอม เก็บข้อมูลแบบเข้ารหัสและจำกัดสิทธิ์เข้าถึง
- เก็บแบบ **passive เท่านั้น** ห้ามเชื่อมต่อ ถอดรหัส หรือดักข้อมูล traffic ของ AP ใดๆ
- เตรียม privacy policy และ privacy label สำหรับ App Store / Play Store (ถ้าเผยแพร่)
- ถ้าเป็นงานวิจัย/วิทยานิพนธ์ ควรผ่านการพิจารณาจริยธรรมการวิจัยในมนุษย์ของมหาวิทยาลัย
- ถ้ากลุ่มตัวอย่างเป็นนักศึกษา ต้องระวังเรื่องความสมัครใจ (ไม่ผูกกับคะแนนหรือการประเมิน)
- การขอข้อมูล AP และ log จากหน่วยงาน (เช่น ITSC) ควรทำผ่านช่องทางที่ได้รับอนุญาต

(ข้อมูลส่วนนี้เป็นแนวทางทั่วไป ไม่ใช่คำปรึกษาทางกฎหมาย ควรตรวจสอบกับผู้เชี่ยวชาญหรือหน่วยงานของมหาวิทยาลัย)

## เฟส 1: พิสูจน์ความเป็นไปได้และวางท่อข้อมูล (สัปดาห์ที่ 1–3)

### 12.1 เป้าหมาย

1. ทำตัวเก็บข้อมูล (data logger) ที่เสถียรบน Android และ iOS
2. **วัดความถี่และคุณภาพของ RSSI จริง** ของแต่ละวิธีเก็บ
3. พิสูจน์ว่า timestamp ของ GPS, Wi-Fi, IMU ซิงก์กันได้
4. ทดลองนำร่องกับทุกโหมดการเดินทางแบบเล็ก ดูว่าสัญญาณมีลายเซ็นแยกโหมดเบื้องต้นหรือไม่
5. ตัดสินใจ go/no-go เรื่องขอบเขต (iOS เข้าโมเดลหลัก หรือเป็นกลุ่มเปรียบเทียบ)
6. ยื่นเรื่อง ethics/PDPA และขอข้อมูลตำแหน่ง AP จาก ITSC ควบคู่ไปเลย

### 12.2 งานฝั่ง Android

| ข้อมูล | วิธี | ความถี่เป้าหมาย |
|---|---|---|
| RSSI/BSSID ของ AP ที่เชื่อมอยู่ | `ConnectivityManager.NetworkCallback` (`FLAG_INCLUDE_LOCATION_INFO`) ร่วมกับการ poll `WifiManager.connectionInfo` | พยายาม 1 Hz แล้ววัดค่าจริง |
| สแกน AP รอบข้าง | `WifiManager.startScan()` / `scanResults` | ตามที่ระบบ throttle (ปกติราว 4 ครั้ง/2 นาที) |
| GPS | `FusedLocationProvider` | 1 Hz |
| Accelerometer / Gyroscope | `SensorManager` | 25–50 Hz |

**ข้อกำหนดทางเทคนิค**
- ใช้ **Foreground Service** พร้อม notification ตลอดการบันทึก
- สิทธิ์ที่ต้องขอ: ตำแหน่งแม่นยำ, ตำแหน่ง background, `NEARBY_WIFI_DEVICES` (Android 13+), `ACTIVITY_RECOGNITION` (ถ้าเก็บเทียบ)
- Flutter: เขียน **platform channel** เองสำหรับ RSSI แบบต่อเนื่อง
- ทุก record ใส่ 2 เวลา: `elapsedRealtimeNanos` (monotonic) และ wall-clock (UTC ms)
- ทดสอบอย่างน้อย 3 ยี่ห้อ (เช่น Samsung, Xiaomi/OPPO, Pixel)
- ทำหน้าแนะนำให้ผู้ใช้ปิดการประหยัดแบตสำหรับแอป

**สิ่งที่ต้องวัด:** ช่วงเวลาระหว่างค่า RSSI ที่ "เปลี่ยน/อัปเดตจริง" (บางเครื่องคืนค่าเดิมซ้ำแม้ poll ถี่), สัดส่วนช่วงที่ไม่มีข้อมูล, แอปถูกระบบฆ่าหรือไม่เมื่อปิดจอ 30 นาที

### 12.3 งานฝั่ง iOS (Shortcuts)

ผู้วิจัยยืนยันแล้วว่า Shortcuts อ่าน RSSI ได้ เฟสนี้จึงมุ่งทดสอบ **วิธีรันที่ให้ความถี่สูงสุดและส่งข้อมูลเข้าแอปได้เสถียร**

| วิธี | แนวคิด | สิ่งที่ต้องเฝ้าดู |
|---|---|---|
| **A. Loop ในรันเดียว** | Shortcut ใช้ Repeat + Wait 1 วินาที วนอ่าน Get Network Details | วนได้นานแค่ไหนตอนปิดจอ ระบบหยุดเองเมื่อไร |
| **B. Automation ตามเวลา** | ตั้งให้รันทุกนาที/ตามช่วง | ความถี่ต่ำ ตั้ง "Run Immediately" ได้หรือไม่ |
| **C. Automation ตามเหตุการณ์** | Wi-Fi เชื่อมต่อ/เปลี่ยน, เปิดแอป ฯลฯ | จับช่วง roaming ได้หรือไม่ |

> ยังไม่ได้ยืนยันว่าวิธี A วนต่อเนื่องได้นานเท่าไรเมื่อล็อกจอ ต้องวัดเอง ผลตรงนี้เป็นจุดตัดสินของทั้งเฟส

**การส่งข้อมูลเข้าแอป**
- Shortcut เรียก **App Intent** ของแอป (เช่น `LogWifiSample(rssi, bssid, ssid, timestamp)`) ดูตัวอย่างแนวคิดในภาคผนวก 15.5
- แอปเขียนลงฐานข้อมูลในเครื่อง (ถ้า intent ทำงานนอกโพรเซสหลัก ใช้ App Group container ร่วมกัน)
- เปิด **Background mode: location** เพื่อเก็บ GPS ต่อเนื่อง และเก็บ IMU (Core Motion) เท่าที่ระบบอนุญาต
- ทางสำรอง: ให้ Shortcut ต่อบรรทัดลง CSV แล้วนำเข้าทีหลัง
- ใส่ timestamp ทั้งใน Shortcut (Current Date) และฝั่งแอปตอนรับ เพื่อวัดความหน่วง

**การทดสอบเสริม:** แอปเล็กๆ เรียก `NEHotspotNetwork.fetchCurrent()` ทุก 1 วินาที ดูว่า `signalStrength` เป็นค่าจริงหรือ 0.0 ใช้เครื่องอย่างน้อย 2 รุ่น/2 เวอร์ชัน iOS

**สิ่งที่ต้องวัด:** ช่วงเวลาระหว่างตัวอย่าง (median, p95, max gap) ทั้งจอเปิดและจอปิด; ระยะเวลาสูงสุดที่เก็บต่อเนื่องได้โดยไม่แตะเครื่อง; ความละเอียดของ RSSI (กี่ระดับ จำนวนเต็มหรือไม่); ความหน่วงระหว่างอ่านค่าใน Shortcut กับเวลาที่แอปบันทึก

### 12.4 การทดลองนำร่อง

| ชุดทดลอง | รายละเอียด | จุดประสงค์ |
|---|---|---|
| ทดสอบนิ่ง | วางเครื่องกับที่ 10 นาที ใกล้ AP | วัดสัญญาณรบกวนพื้นฐานของ RSSI |
| ทดสอบเส้นทางเดียวกัน | เส้นทางในมหาวิทยาลัย ~2 กม. ผ่านหลายอาคาร เดิน/จักรยาน/มอเตอร์ไซค์/รถ อย่างละ 3 รอบ | ดูลายเซ็นต่างโหมดบนเส้นทางเดียวกัน |
| ทดสอบตำแหน่งวางเครื่อง | กระเป๋า / มือ / ที่ยึด | ผลของการบังตัว |
| ทดสอบหน้าจอ | จอเปิด vs ปิด | ยืนยันว่าการเก็บเบื้องหลังทำงาน |
| ทดสอบข้ามอุปกรณ์ | Android 2–3 รุ่น + iPhone 2 รุ่น วางพร้อมกันบนยานพาหนะเดียว | ประเมินความต่างของอุปกรณ์ |

บันทึกโหมดจริงด้วยปุ่ม Start/Stop ในแอปทุกครั้ง และจดสภาพจราจร/จุดหยุด

### 12.5 เกณฑ์ Go / No-Go (ปรับค่าได้หลังเห็นข้อมูลจริง)

| หัวข้อ | เกณฑ์ผ่านที่แนะนำ | ถ้าไม่ผ่าน |
|---|---|---|
| Android: median ช่วงระหว่างตัวอย่าง RSSI | ≤ 2 วินาที | ใช้ window ยาวขึ้น หรือลดฟีเจอร์ที่ใช้อนุพันธ์ |
| iOS: median ช่วงระหว่างตัวอย่าง | ≤ 5 วินาที และเก็บต่อเนื่องจอปิดได้ ≥ 30 นาที | iOS เป็นกลุ่มเปรียบเทียบ ใช้เฉพาะฟีเจอร์หยาบ (ค่าเฉลี่ย/ความแปรปรวน/roaming) |
| สัดส่วนช่วงขาดหาย (gap > 30 วินาที) | < 30% ของเวลาในอาคาร | เพิ่มฟีเจอร์ "ขาดหาย" และพิจารณาเส้นทางที่ครอบคลุมกว่า |
| Time sync GPS–Wi-Fi–IMU | คลาดเคลื่อน < 1 วินาที | แก้ pipeline ก่อนเก็บจริง |
| สัญญาณแยกโหมด | เห็นความต่างในสถิติเบื้องต้นอย่างน้อย เดิน vs ยานยนต์ | ทบทวนสมมติฐานก่อนเข้าเฟส 2 |

(ตัวเลขเกณฑ์เป็นข้อเสนอเริ่มต้น ไม่ใช่มาตรฐาน)

### 12.6 งานคู่ขนานในเฟส 1

- **Ethics/PDPA:** ยื่นขอรับรองจริยธรรม เตรียมใบยินยอม ออกแบบการตัดช่วงที่อยู่บ้าน
- **ข้อมูลตำแหน่ง AP:** ทำหนังสือขอ BSSID → พิกัด จาก ITSC เป็นแผนหลัก ตรวจว่า JumboMap เปิดเผย BSSID จริงหรือไม่ แผนสำรอง: ประมาณตำแหน่ง AP จากข้อมูล GPS+RSSI ที่เก็บเอง
- **รับสมัครอาสาสมัคร** สำหรับเฟส 2 ให้หลากหลายอุปกรณ์/โหมด

### 12.7 ผลลัพธ์ที่ต้องส่งมอบเมื่อจบเฟส 1

1. **[ดำเนินการแล้ว: เผยแพร่ GitHub Release v1.0.0 พร้อม app-release.apk และ Runner.ipa]** แอป Android + iOS รุ่นเก็บข้อมูล เผยแพร่บน GitHub Releases (ไฟล์ `.apk` ติดตั้งตรงบน Android และไฟล์ `.ipa` จาก GitHub Actions รองรับทั้งการติดตั้งตรงผ่าน Scarlet บนมือถือ และผ่าน Sideloadly บนคอมพิวเตอร์)
2. ลิงก์ iCloud Shortcut สำเร็จรูป + คู่มือการติดตั้งผ่าน GitHub / Scarlet ([วิดีโอคู่มือ YouTube Shorts](https://www.youtube.com/shorts/Q2H62epJGB8)) และ Sideloadly สำหรับผู้เข้าร่วมฝั่ง iOS
3. รายงานสั้น: ตารางความถี่/ช่องว่างของข้อมูลทุกอุปกรณ์และทุกวิธี

5. บันทึกการตัดสินใจ go/no-go และขอบเขตเฟส 2
6. เอกสาร ethics และสถานะการขอข้อมูล AP

## เฟส 2: เก็บข้อมูลจริง สร้างโมเดล ประเมินผล (สัปดาห์ที่ 4–12)

### 12.8 เป้าหมาย

1. เก็บชุดข้อมูลที่หลากหลายพอสำหรับประเมินแบบ leave-one-participant-out
2. สร้างโมเดลจำแนกโหมดจาก RSSI และเปรียบเทียบกับ baseline อื่น
3. ตอบว่า RSSI มีประโยชน์เมื่อไร (ในอาคาร, GPS แย่, ประหยัดแบต)
4. ประเมินความต่างระหว่าง Android กับ iOS

### 12.9 ขอบเขตคลาส

- **ตั้งต้น 3 คลาส:** เดิน / จักรยาน / ยานยนต์ (มอเตอร์ไซค์ + รถยนต์)
- **คลาสขยาย 4 คลาส:** แยกมอเตอร์ไซค์กับรถยนต์ เมื่อข้อมูลพอ (คาดว่า confusion สูง)
- คลาสเสริม: **หยุดนิ่ง/ติดไฟแดง** เพื่อไม่ให้ป้ายกำกับสกปรก

### 12.10 การออกแบบการเก็บข้อมูล

| หัวข้อ | แนวทาง |
|---|---|
| จำนวนผู้เข้าร่วม | 15–30 คน อย่างน้อย 5 คนต่อโหมดหลัก |
| อุปกรณ์ | Android ≥ 3 ยี่ห้อ, iPhone ≥ 2 รุ่น |
| ปริมาณต่อโหมด | เป้าหมาย ≥ 5 ชั่วโมง/โหมด และ ≥ 30 ทริป/โหมด |
| ความหลากหลาย | หลายเส้นทาง หลายช่วงเวลา (เช้า/เที่ยง/เย็น/ฝนตก) หลายตำแหน่งวางเครื่อง |
| ป้ายกำกับ | ผู้ใช้กดเลือกโหมดเอง + ตรวจกับความเร็ว GPS ตัดช่วงที่ขัดแย้ง |
| ระยะเวลาเก็บ | 4–6 สัปดาห์ |
| ตรวจคุณภาพรายวัน | สคริปต์สรุป: จำนวนตัวอย่าง, ช่องว่าง, ค่า RSSI ผิดปกติ, ทริปที่ขาด GPS |

### 12.11 การเตรียมข้อมูล ฟีเจอร์ โมเดล และการประเมินผล

ใช้ตามหัวข้อ 8 (Pipeline, ฟีเจอร์, โมเดล A/B, Ablation) และหัวข้อ 9 (ตัวชี้วัด, การแบ่งข้อมูล, สถานการณ์ที่ต้องรายงานแยก) โดยเพิ่มข้อกำหนดของเฟส 2:

- รายงานค่าเฉลี่ยพร้อมช่วงความเชื่อมั่น (bootstrap หรือส่วนเบี่ยงเบนข้ามผู้เข้าร่วม)
- ทดสอบนัยสำคัญระหว่างชุดฟีเจอร์ (เช่น paired test ข้าม fold)
- วิเคราะห์ข้อผิดพลาด: ดูทริปที่ทายผิดเพื่อหาสาเหตุ (ช่องว่างข้อมูล, รุ่นเครื่อง, จุดหยุด)
- ทดสอบความทนทาน: ฝึกบน Android ทดสอบบน iOS (และกลับกัน)
- ถ้าได้ตารางตำแหน่ง AP: เพิ่มฟีเจอร์ความเร็วโดยประมาณจาก roaming

### 12.12 ตารางเวลาแนะนำ

| สัปดาห์ | งาน |
|---|---|
| 4 | สรุปผลเฟส 1 ปรับแอป เปิดรับอาสาสมัคร ปฐมนิเทศ |
| 5–8 | เก็บข้อมูลหลัก ตรวจคุณภาพรายสัปดาห์ แก้ปัญหาเครื่อง/ผู้ใช้ |
| 7–9 | สร้าง pipeline ฟีเจอร์ + โมเดลต้นแบบบนข้อมูลที่ได้มาแล้ว |
| 9–10 | เก็บข้อมูลเสริมจุดอ่อน (โหมด/อุปกรณ์ที่ขาด) |
| 10–11 | ทดลอง ablation และประเมินผลเต็มรูปแบบ |
| 12 | เขียนรายงาน/บทความ ทำชุดข้อมูลนิรนามสำหรับแชร์ (ถ้า ethics อนุญาต) |

### 12.13 ผลลัพธ์ที่ต้องส่งมอบเมื่อจบเฟส 2

1. ชุดข้อมูลนิรนามพร้อม data dictionary
2. โค้ด pipeline (Python) ทำซ้ำได้: โหลด → ซิงก์ → ฟีเจอร์ → โมเดล → ประเมินผล
3. ตารางผล ablation (G / I / R / R+I / fusion) และผลแยกตามสถานการณ์/แพลตฟอร์ม
4. รายงานฉบับเต็ม/ร่างบทความ ที่ตอบชัดว่า RSSI มีคุณค่าเมื่อไร
5. ข้อเสนอต่อยอด (RSSI ในอาคาร, ผนวกตารางตำแหน่ง AP เพื่อประมาณความเร็ว, ขยายมหาวิทยาลัยอื่น)

## 14. คำถามที่ยังต้องยืนยัน

**จากฉบับเดิม**
1. JumboMap แสดงข้อมูล AP/BSSID หรือไม่ และมีวิธีขอข้อมูลอย่างถูกต้องอย่างไร (หัวข้อ 5.3)
2. จะขอ log ฝั่งเครือข่ายจาก ITSC ร่วมด้วยหรือไม่ (ถ้าได้ จะรวมสองแหล่งข้อมูลได้ เป็นจุดเด่นของงาน)
3. เก็บข้อมูลเองคนเดียวหรือมีผู้ร่วมทดลองหลายคน
4. เป้าหมายคือ **แทน GPS** หรือ **เสริม GPS** (ส่งผลต่อวิธีเปรียบเทียบ baseline)
5. พื้นที่ทดลองอยู่ในอาคาร กลางแจ้ง หรือทั้งสองแบบ
6. มี Mac และ iPhone สำหรับทดสอบหรือไม่

**เพิ่มจากการวิเคราะห์ล่าสุด**
7. ผู้วิจัยเก็บ RSSI บน iOS ด้วยวิธีใด (loop ในรันเดียว / automation) และได้ความถี่จริงประมาณเท่าไร ทั้งจอเปิดและจอปิด
8. ค่าที่ Shortcut คืนเป็น dBm จำนวนเต็มหรือไม่ และส่งเข้าแอปได้อย่างไรในปัจจุบัน

## 15. ภาคผนวก: ความรู้พื้นฐานและโค้ดตัวอย่าง

### 15.1 RSSI อ่านอย่างไร

| ค่า RSSI | ความหมาย |
|---|---|
| −30 dBm | แรงมาก (ติดเราเตอร์) |
| −50 dBm | ดีมาก |
| −67 dBm | ดี |
| −70 dBm | พอใช้ |
| −80 dBm | แย่ |
| −90 dBm | แทบใช้ไม่ได้ |

ยิ่งใกล้ 0 ยิ่งแรง; ลด 3 dB = กำลังลดครึ่ง; ลด 10 dB = เหลือ 1 ใน 10

### 15.2 โค้ด Dart: ตัวกรอง RSSI และฟีเจอร์พื้นฐาน

```dart
import 'dart:math';

/// กรอง RSSI ด้วย exponential moving average
class RssiFilter {
  final double alpha; // 0..1 ยิ่งน้อยยิ่งเรียบ
  double? _value;
  RssiFilter({this.alpha = 0.3});

  double update(double rssi) {
    _value = _value == null ? rssi : alpha * rssi + (1 - alpha) * _value!;
    return _value!;
  }
}

/// ระยะระหว่างสองพิกัด (เมตร)
double haversine(double lat1, double lon1, double lat2, double lon2) {
  const r = 6371000.0;
  double rad(double d) => d * pi / 180;
  final dLat = rad(lat2 - lat1), dLon = rad(lon2 - lon1);
  final h = pow(sin(dLat / 2), 2) +
      cos(rad(lat1)) * cos(rad(lat2)) * pow(sin(dLon / 2), 2);
  return 2 * r * asin(sqrt(h));
}

/// อัตราเปลี่ยนเฉลี่ยของ RSSI ในหน้าต่างเวลา (หน่วยเดิม/วินาที)
double meanAbsRate(List<double> rssi, List<double> tSec) {
  if (rssi.length < 2) return 0;
  double sum = 0;
  for (var i = 1; i < rssi.length; i++) {
    final dt = tSec[i] - tSec[i - 1];
    if (dt > 0) sum += (rssi[i] - rssi[i - 1]).abs() / dt;
  }
  return sum / (rssi.length - 1);
}
```

### 15.3 ตัวอย่างการคำนวณความเร็วโดยประมาณจากการ roaming

```dart
// apMap: BSSID -> (lat, lon)  ← มาจากตารางตำแหน่ง AP (หัวข้อ 5)
double? roamSpeedKmh(
  String fromBssid, String toBssid, double dtSec,
  Map<String, ({double lat, double lon})> apMap,
) {
  final a = apMap[fromBssid], b = apMap[toBssid];
  if (a == null || b == null || dtSec <= 0) return null;
  final meters = haversine(a.lat, a.lon, b.lat, b.lon);
  return (meters / dtSec) * 3.6; // m/s -> km/h
}
```

> หมายเหตุ: เพราะ sticky client ความเร็วที่ได้เป็นค่าประมาณ ควรใช้เป็นฟีเจอร์ร่วมกับตัวอื่น ไม่ใช่ตัวตัดสินเดี่ยวๆ

### 15.4 Platform Channel (โครงสร้างแนวคิด)

- **Android (Kotlin):** อ่าน BSSID และ RSSI (dBm) ผ่าน `NetworkCallback` + `WifiManager.connectionInfo` (ตัวหลังถูก deprecate แต่ยังใช้ได้ ควรเทียบกับตัวแรก)
- **iOS (Swift):** วิธี 1 คือ Shortcut + App Intent (RSSI dBm) วิธี 2 คือ `NEHotspotNetwork.fetchCurrent` ได้ BSSID และ `signalStrength` (0.0–1.0 ถ้าคืนค่าจริง) ต้อง entitlement "Access WiFi Information" และสิทธิ์ Location (iOS 14 ขึ้นไป)
- ทั้งสองฝั่งส่งข้อมูลกลับไปยัง Dart ผ่าน `MethodChannel` / `EventChannel` เป็น stream เดียวกัน พร้อมฟิลด์ `rssi_unit` และ `rssi_source`

### 15.6 ตัวอย่าง Python: วัดความถี่และช่องว่างของ RSSI (ใช้ในเฟส 1)

```python
import pandas as pd

df = pd.read_csv("pilot.csv")
w = df[df["source"] == "wifi_connected"].sort_values("t_utc_ms").copy()

# ช่วงเวลาระหว่างตัวอย่าง (วินาที) แยกตามเครื่องและ session
w["dt"] = w.groupby(["device_model", "session_id"])["t_utc_ms"].diff() / 1000

# นับเฉพาะตัวอย่างที่ RSSI เปลี่ยนจริง (ตัดค่าซ้ำจากการ poll)
w["changed"] = w.groupby(["device_model", "session_id"])["rssi_raw"].diff().fillna(1) != 0

summary = (
    w.groupby(["platform", "device_model"])["dt"]
     .agg(median="median", p95=lambda s: s.quantile(0.95), max="max")
)
gap_ratio = (
    w.assign(gap=w["dt"] > 30)
     .groupby(["platform", "device_model"])["gap"].mean()
)
print(summary)
print(gap_ratio)
```
